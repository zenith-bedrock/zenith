# .NET / C# opportunities (2026-11-13)

Survey of platform features Zenith did not use and what each would buy. Method: grep of `src/` and `libs/` for each feature, plus the Dockerfile and build props, then a measurement before any adoption (`--runtime-load`, `--tick-jitter` and BenchmarkDotNet are in the repo). **Every item below is now closed: adopted with its measurement, or evaluated and deliberately not adopted with the number that says why.** The first survey was a hypothesis; items 3 and 5 turned out to be mostly wrong once measured, and that is recorded rather than hidden.

Toolchain today: SDK 10.0.303, `net10.0`, `LangVersion 14`, Nullable on, analyzers `latest`. A clean build (`dotnet build zenith.sln -c Release --no-incremental`) has 0 warnings; incremental builds hide warnings of projects that were not recompiled, so always check with `--no-incremental`.

## Already used well (no action)
`Span`/`stackalloc` (105 files), `ArrayPool`, `BinaryPrimitives`, `Channels`, `readonly record struct` (57), `required`, primary constructors, collection expressions, `GeneratedRegex`, a source generator (`zenith.PacketGenerator`), `FrozenDictionary` in one file, `field` keyword in four places.

## 1. Debug logging that allocated while disabled — DONE
`ILogger.Debug(string)` received an already-built string, so every `Debug($"...")` formatted and allocated even with Debug off (about 110 call sites across Session, Gameplay, RakNet).
Now `ILogger.Debug(ref DebugLogHandler)` (default interface method, `libs/logging/DebugLogHandler.cs`) is picked by the compiler for interpolated strings: with Debug off nothing is formatted or allocated and the interpolated expressions are not evaluated; with Debug on the output is identical. No call site changed. `DebugLoggingTests` pins both behaviours and that 10,000 disabled calls allocate 0 bytes.
`nethernet` is a packable library that depends on no other Zenith package, so `INetherNetLogger` carries its own copy of the mechanism (`IsDebugEnabled`, `Debug(ref NetherNetDebugHandler)`, `NetherNetDebugHandler`); the Zenith adapter forwards `IsDebugEnabled`, and the `Null`/`Prefixed` loggers honour it. Its string-concatenation Debug calls were rewritten as single interpolations so they take the same path. Tests: `src/nethernet.Tests/Axolotl/DebugLoggingTests.cs`.
Scope and limits: only Debug has a handler, because it is the only level meant to be off in production; Info/Warning/Error calls are emitted by default, so building their text is the work, not waste. `IsDebugEnabled` is still needed when the arguments are prepared outside the string (LINQ/joins, e.g. `NetworkSession` outbound).

## 2. First tick and GC settings — DONE (ReadyToRun adopted; GC mode left as is, with numbers)
New scenario `dotnet run -c Release --project src/zenith.Benchmarks -- --runtime-load --cold-start`: the mixed-roster tick (10 players, 100 actors) with **no warmup**, reporting the JIT work done while the loop runs (`JitInfo`) and the slowest first ticks. Windows 11 dev machine, 400 ticks, 3-5 runs each:

| Build | First tick | Methods JIT-compiled during ticks | JIT time during ticks | Ticks over 5 ms |
|-------|-----------|-----------------------------------|-----------------------|-----------------|
| JIT (what `dotnet run` and the old publish gave) | 108-124 ms | about 1,510 | 146-160 ms | 4-5 |
| ReadyToRun publish | 55-63 ms | about 561 | 58-66 ms | 3 |
| ReadyToRun + `TieredPGO=0` | 47-53 ms | about 561 | 51-55 ms | 3 |
| ReadyToRun + `TieredCompilation=0` | 80-92 ms | n/a | 109-121 ms | 4-5 (worse) |

- **Adopted:** ReadyToRun on every RID-specific publish (`zenith.csproj`: `PublishReadyToRun` when a `RuntimeIdentifier` is set; the release workflow already publishes `-r linux-x64`, and both Dockerfiles now publish with `--use-current-runtime`). It halves the first tick and the number of methods compiled at run time; a plain `dotnet build`/`run` is unchanged. A `linux-x64` publish from the Windows machine confirmed the precompiled assemblies (`zenith.dll` 3.56 MB against 2.15 MB of IL only). **Not verified inside Docker** (no Docker on the machine); the images need one build to confirm.
- **Not adopted:** `TieredPGO=0` saves about 5 ms on the first tick but gives up profile-guided optimisation for a process that runs for days; steady-state ticks are 0.4-1 ms against a 50 ms budget, so there is nothing to win there. `TieredCompilation=0` is worse.
- **Still open inside this item:** the first tick is still about 55 ms, above the 50 ms budget, because 561 methods (generic instantiations across assemblies, lambdas) are still compiled on first use. A real server pays this once, on the first player; a startup warm-up tick over the join path would absorb it before anyone connects. That is a product decision (boot time against first-join stall), not a runtime setting, so it is left to the roadmap.
- **GC pauses are now measured:** the runtime log line prints `gcPause=<ms>/30s`, the diagnostics layout has `runtime.gc.pause-ms` (and so the Meter, item 7), the harness prints `gcPause=` per scenario, and the server logs its GC mode once at startup (`gc: workstation concurrent=... latency=...`). In the 400-tick scenario the default configuration spends 12-15 ms in GC (4 gen0 and 1 gen1; a gen2 in about one run in five adds about 15 ms).
- **GC mode left as is.** `DOTNET_gcConcurrent=0` made this scenario run with no collection at all (a larger gen0 budget), which looks like a win but is an artefact of a tiny heap: with concurrent GC off every gen2 is a blocking collection whose pause grows with the resident heap (overlays, chests, columns), exactly the case background GC exists for. Adopting it needs a large-heap soak first, which does not exist yet. The new telemetry (`gcPause` per 30 s in production) is what would justify the change.

## 3. `TimeProvider` — DONE (adopted where a test could not reach the clock; the broad plan was wrong)
The survey assumed real clocks caused the flaky tests. Reading them showed otherwise: `TickSchedule` is pure (it takes timestamps), the raknet tests already back-date `LastSeen`/frame times, the token tests build claims relative to now, and `TickPacingTests` measures the OS timer itself, which a fake clock cannot replace. What was really unreachable:
- **Franchise key cache** (6-hour refresh, never tested) kept the key list and its expiry in two unsynchronised statics. It is now `FranchiseKeyCache`: one immutable snapshot (keys + expiry) behind a volatile reference, `TimeProvider`-driven, with tests for exact expiry, a single fetch under 16 concurrent callers, a failed fetch not being cached, no stale keys past expiry, and a cancelled waiter not poisoning the cache. `FranchiseTokenValidator` takes the same `TimeProvider`, so `exp`/`nbf` (including the 60-second skew allowance) are tested to the second, and a token accepted now is rejected after the clock passes its expiry.
- **Rate limiters:** `IpRateLimiter` and `TokenBucketRateLimiter` each had their own `Func<long> nowMs` seam; both now take a `TimeProvider`, so there is one clock abstraction in the codebase (`FakeClock` in the two test projects, no package needed). A refill-at-the-exact-millisecond test was added for `IpRateLimiter`.
- **Left alone on purpose:** the RakNet session timestamps (tests already control them), the NetherNet 10-second key wait (socket-bound test), `PreciseWaiter`/`GameClock` (they exist to measure real time).

## 4. `System.Threading.Lock` — DONE
All 18 `private readonly object` lock fields in production code (16 files) are now `Lock` (RakNet server/session, session host, mailboxes, `PlayerDig`/`Intents`/`Windows`/`ChunkTracker`, game rules, server lifecycle, `Blocks`/`Tools`/`BlockLoot`/`DigProfiles`, `LevelDbChunkStorage`, `DB`). No `Monitor` calls existed, so nothing else changed; the compiler now rejects locking on the wrong type. Not converted: `lock (bucket)` in `IpRateLimiter` (it locks the bucket's own data, not a dedicated gate) and the two benchmark fields that exist to compare lock primitives.

## 5. `FrozenDictionary` / `FrozenSet` for read-only catalogs — EVALUATED, not adopted for speed
Measured (`Dictionary` against `FrozenDictionary`, string keys, 4,096 random hits, Release): about 21-33 ns against 14-17 ns for a 24-entry table and 23-32 ns against 15-22 ns for a 1,600-entry palette, a saving of **7-9 ns per lookup**. The catalogs (armor, food, durability, palettes, recipes) are read per event (damage, eating, breaking a block, crafting), a few dozen times per tick at most; even 10,000 lookups per tick would save under 0.1 ms of a 50 ms budget. Not worth the churn. Where it already is (`Tools`, `BlockLoot`) it stays, because there it is the immutable published generation that removed a real race, not an optimisation. Recipe and creative catalogs keep their explicit compose, freeze, read-only lifecycle (ADR §133).

## 6. Warnings as errors and analyzers — DONE
`TreatWarningsAsErrors` is on (NuGet audit advisories `NU1901`-`NU1904` excluded: they come from an external feed). On top of the default analyzers, `.editorconfig` enables a curated set at warning level, so a finding fails the build: culture-dependent formatting and parsing (CA1304/1305/1311), discarded `ValueTask` (CA2012), throw helpers (CA1512/1513), reused `JsonSerializerOptions` (CA1869), specific exception types (CA2201/2208), `Enumerable` on indexable collections (CA1826), `Activator.CreateInstance<T>` (CA2263), forwarded cancellation tokens (CA2016), `SuppressFinalize` (CA1816), constant-array and `IsEmpty` allocations (CA1861/1836, off in tests and benchmarks).
`AnalysisMode=Recommended` was evaluated first: 1,744 distinct findings, about 1,500 of them CA1707 (underscored test names) and naming rules. The rest were triaged; what was fixed:
- **Culture:** about 75 sites (ICE/SDP/signaling text, IP parsing, log level casing in the Turkish-i sense, the log-file stamp, the protocol-import and bedrock-data generators and reports, which now produce the same bytes on a pt-BR machine as on an en-US one).
- **Discarded `ValueTask`s in `World`** (9 write-behind calls): now `WriteBehind(...)`, which consumes a completed task and observes a pending one, logging a failure instead of losing it as an unobserved exception.
- **`System.Exception` thrown for an unknown IP version** in the RakNet reader is now `InvalidDataException`; `Activator.CreateInstance(typeof(T))` is generic; `JsonSerializerOptions` instances are cached (diagnostics, protocol-import); argument-validation uses the throw helpers.
- **Deliberately not enabled** (reasons in `.editorconfig`): CA1707, CA1051 (public fields on wire models), CA1805 (explicit defaults document wire defaults), CA1859 (would replace seams such as `ILogger` by concrete types), CA5351 (MD5 is mandated by the Bedrock offline UUID).
- **CA1001 reviewed, not enabled:** the 13 flagged types (`ZenithServer`, `NetworkSession`, `World`, `RakNetServer`, `NetherNetTransport`, the two signaling classes, `WriteBatch`, `Assembler`, `FranchiseKeyCache` and three benchmarks) were each checked. Every one already has an explicit teardown (`World` disposes its broker in `StopGenerationAsync`, `NetworkSession` disposes its token source when the stream worker ends, the signaling sockets are disposed in `Stop`, the transport disposes its runner), and `MemoryStream`/`SemaphoreSlim` without a wait handle need no disposal. No leak found; making them `IDisposable` would add a second way to stop them, so the rule stays off.
- `EnforceCodeStyleInBuild` stays off: it would turn about 300 style findings into errors for no defect found.

## 7. `System.Diagnostics.Metrics` as a bridge — DONE
`libs/diagnostics` stays the source of truth and the only thing the tick touches. `DiagnosticsMeter` publishes it as a `Meter` named `Zenith.Diagnostics` through observable instruments only, so values are read when a collector asks and recording remains allocation-free (tested: 10,000 `Set` calls allocate 0 bytes with the meter alive). Counters and gauges map one to one (same names, `category` tag); a timing becomes `name.count`, `name.total`, `name.max`, `name.last` in seconds. The server gives units (`By`, `By/s`, `ms`; `tick.tps` is stored x1000 and says so as `{milli-tps}`) and disposes the meter at shutdown. New gauge `runtime.gc.pause-ms`. Read it with `dotnet-counters monitor -n zenith --counters Zenith.Diagnostics` or any OpenTelemetry meter exporter. Tested with a `MeterListener` (values, units, category, seconds conversion, and the server's own layout); **not exercised against a real `dotnet-counters`/OTLP exporter** here.

## Considered and not recommended
- **Native AOT:** YamlDotNet and reflection use make it costly; ReadyToRun (item 2) gets most of the startup benefit.
- **`System.IO.Pipelines`:** transport is UDP datagrams (RakNet/NetherNet), not a byte stream.
- **SIMD (`Vector128`), `InlineArray`, `SearchValues`, `unsafe`:** only if a profiler points at them. The obvious scalar candidate, `FastNoiseLite`, is not a measured bottleneck.
- **C# 14 extension members and other new syntax:** marginal ergonomics.
- **Running systems in parallel inside a tick:** the largest raw-performance lever, but it contradicts the single-writer rule (ADR §97). An architecture decision, not a missing language feature.
- **`FrozenDictionary` everywhere and `TieredPGO=0`:** measured, small, see items 5 and 2.
