# ADR §142 — Real Mojang game data, owned end-to-end: a first-party `.brarchive` reader, and the real vanilla creative catalog

> Part of the [decision log](README.md). Code and docs cite this record as `ADR §142`.

**Context:** asked to audit how reference servers (PocketMine-MP, PowerNukkitX, Dragonfly) load their
creative/survival/crafting catalogs and whether Zenith's own approach — one hand-typed
`RegisterBlock`/`RegisterTool` call per Creative item, a fake single unnamed group, `recipes.nbt`
nonexistent — was adequate. It wasn't: `creative_items.json` (1,875 real vanilla items / 123 real
groups) was already embedded in the assembly since an earlier phase but loaded by nothing (ADR §38's
own "Deferred" line named this gap explicitly back in July and it was never picked back up). Follow-up
direction was explicit: go the *correct* path for Zenith's clean/malleable/DX-focused architecture,
not the fastest hack, and specifically research how Mojang's own BDS handles this data.

**`.brarchive`, reverse-engineered and independently verified, not assumed:** BDS ships recipes as
`behavior_packs/vanilla/__brarchive/recipes.brarchive` — a real, if obscure, community-documented
container format (`Cubeir/BrArchive.Net` on GitHub: 8-byte magic, `u32` entry count, `u32` format
version, then a flat table of fixed 256-byte entry records — 1-byte name length + 247-byte padded
name + `u32` content offset + `u32` content length — then one concatenated data block). Verified
byte-for-byte against a real local BDS install rather than trusted from the library alone: all 821
entries decode to plain, current vanilla recipe JSON with zero parse failures (456 shaped, 207
shapeless, 95 furnace, 61 brewing_mix, 2 brewing_container). `item_catalog.brarchive`'s single entry
does *not* decode the same way (a second, still-undocumented `\x7fMCB`-tagged compiled sub-format) —
left unsolved, not needed, since `creative_items.json` already covers the same ground through an
independent, already-decoded source. No reference server in `D:\Development\bedrock\` (endstone,
PocketMine, PowerNukkitX, Dragonfly, gophertunnel) parses raw BDS data at all — they all consume
already-decoded derivative packages. A small first-party `.brarchive` reader is a genuine step past
what any of them do, not a shortcut.

**Choice, two parts:**

1. **`tools/gamedata-import`** — a new dev-time-only companion tool, same shape as
   `tools/protocol-import` (never ships, never runs at server runtime). `BrArchiveReader` implements
   the verified container format directly (no dependency on the community library — the format is
   small and fully verified, matching Zenith's existing discipline of owning its data code, like
   `Zenith.Nbt` being in-repo rather than a NuGet package). `VanillaRecipeImporter` converts every
   entry's real recipe JSON into one `Zenith.Nbt` document — reusing the existing NBT codec/gzip
   convention every other `src/zenith/data/*` file already follows, not a new format. Output:
   `src/zenith/data/recipes.nbt` (16 KB gzip, down from the 447 KB source archive), checked in like
   every other data file, regenerated by re-running the tool against a newer BDS install. **Not yet
   wired to any gameplay system** — `RecipeRegistry` stays hand-curated/shapeless; consuming real
   shaped-recipe data is a separate, real engine decision (shape matching or a documented flattening
   policy) made with real data in hand, not bundled into this pass. `RecipesDataTests` is a pipeline
   integrity check only (resource decodes, known recipe matches source JSON, all 5 real recipe types
   present), not a gameplay test.

2. **`CreativeItemsLoader`** — loads `creative_items.json` for real: block-form entries carry a
   `block_state_b64` field (a small Bedrock-LE NBT compound); its `network_id` int tag is the exact
   same integer `block_palette.nbt` already uses as Zenith's own block runtime id (verified
   byte-for-byte for `minecraft:oak_planks` in both files), so no general multi-state block resolver
   is needed — decode the blob, read the tag. Pure items resolve through the existing
   `ItemPalette.Require`. Real vanilla data uses a `"minecraft:empty"` icon sentinel on ~30 groups
   (client falls back to the group's first item) — resolved to an empty `StackId`, matching
   `NetworkItemStack.Empty`'s existing meaning in `CreativeContentBuilder`.

   `CreativeCatalog.CreateDefault` now builds from this loader instead of one `RegisterBlock`/
   `RegisterTool` call per item, filtered through the **same safety gate it always used, unchanged**:
   a block is exposed only if it has a `Blocks` name *and* a curated `DigProfiles` row; a pure item
   only if it's one of `Tools`'s 12 curated tools. Running that gate against the real 1,875-item
   catalog surfaced a real scope question mid-implementation: `DigProfiles` already has 20 more rows
   than the 13 blocks the old hand-typed list registered — all 14 ore/deepslate-ore variants,
   cobblestone, deepslate, oak_leaves, and the ADR §137 ground-cover set (short_grass/dandelion/
   poppy) — each with real dig behavior and a settled passability classification already, just never
   previously creative-exposed. Decided (explicit call, not a silent default): expose all of them —
   the gate's job is deciding *safety*, not gating catalog growth a second time by a separate,
   undocumented allow-list. Final catalog: **45 items across 19 real vanilla groups** (13 pinned
   blocks + 20 newly-eligible blocks + 12 tools; up from 25 items in one fake unnamed group).
   `CreativeContentBuilder` now emits real `CreativeGroupEntry[]` (category/name/icon) and each
   item's real `GroupIndex` instead of the old single hardcoded placeholder.

   The 25 pre-existing `CreativeCatalog.Stone`/`.DiamondPickaxe`/etc. `const uint` wire ids are kept
   as **pinned, stable net ids** rather than replaced by a fully sequential/data-order encoding —
   dozens of existing tests reference them as known-good creative net ids for exercising
   `CraftCreative` wire flows, and an opaque wire id has no vanilla-fidelity requirement to justify
   breaking that contract. Any item eligible through the safety gate but not one of the 25 pinned
   ones (the 20 newly-exposed blocks) gets an auto-assigned id above the pinned range.

**Test-infra fallout, a real and generically useful fix, not a workaround:** the richer real payload
(45 items / 19 named groups, 1.6 KB encoded) exceeds the 1400-byte test session MTU, so
`GameModeSystem_remints_creative_content_on_every_mode_change` — which had asserted the encoded
packet's bytes were a contiguous span across raw captured UDP datagrams — started failing once the
packet needed RakNet split-packet fragmentation across multiple datagrams to send at all. Fixed by a
new `ReassembleApplicationPackets` test helper that decodes captured datagrams into `FrameSet`/
`Frame`s and reassembles split ones exactly like `RakNetSession.HandleFragment` does (index-ordered
concat by `SplitInfo.Id`) before searching for the expected packet's bytes — the first test in the
suite to exercise a payload large enough to need this, but a correct, reusable pattern for any future
one that does.

**Non-goals:** decoding `item_catalog.brarchive`'s inner `MCB`-tagged compiled sub-format; consuming
shaped-recipe data in `RecipeRegistry` (real data unlocks this as a well-scoped future decision, not
attempted here); running `gamedata-import` (or requiring a BDS install) at server runtime.
